# ADR-001：使用六边形架构隔离基础设施

- 状态：已接受
- 日期：2026-08-18
- 负责人：服务团队
- 决策人：架构负责人
- 关联需求/问题：生产级工程母版基线

## 背景

服务需要独立于 GoldenDB、Redis、OBS 和 HTTP 的实现细节持续演进，同时让自主编码代理能够清晰理解。若业务代码全面直接耦合框架，变更和隔离测试的成本会不断增加。

## 决策驱动因素

- 明确的依赖方向与所有权
- 无需基础设施即可测试应用行为
- 基础设施适配器可替换
- 通过 ArchUnit 进行机械化约束

## 备选方案

### 传统 Controller-Service-Mapper 分层

- 收益：团队熟悉，初期代码紧凑。
- 成本/风险：基础设施类型容易向内层泄漏，功能增长后边界会逐步弱化。

### 六边形架构

- 收益：端口稳定、领域层不依赖框架、测试可隔离、适配器所有权清晰。
- 成本/风险：类型与映射更多，需要持续遵守包结构规则。

## 决策

使用入站/出站端口，由应用服务编排用例。框架和厂商依赖只允许存在于适配器或配置层。使用 ArchUnit 强制执行关键依赖规则。

## 后果

- 新增外部集成时，需要由领域层定义端口，并提供对应适配器。
- 小功能会增加少量结构性代码。
- 跨系统一致性必须在应用工作流中显式体现，而不是隐藏在基础设施内部。

## 验证

- `HexagonalArchitectureTest` 通过。
- 单元测试使用端口测试替身实例化应用服务。

## 回滚或取代

如果实际度量表明其复杂度超过变更安全收益，可以用新的 ADR 取代本决策；迁移期间仍须保持依赖方向正确。
