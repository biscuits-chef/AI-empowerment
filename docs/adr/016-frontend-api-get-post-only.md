# ADR-016：前端业务接口仅使用 GET 与 POST

- 状态：已接受
- 日期：2026-09-14
- 负责人：项目交付负责人
- 决策人：用户确认
- 关联需求/问题：统一前后端 HTTP 方法白名单，禁止面向前端的 PUT、PATCH、DELETE 等方法

## 背景

现有前端契约使用 PATCH 修改会话、DELETE 删除会话和文件、PUT 提交回答反馈，其余查询和命令主要使用 GET 与 POST。用户明确要求所有前端交互接口只使用 GET 和 POST，并将所有非 GET 方法改为 POST。该约束跨越后端控制器、前端 HTTP 网关、接口文档、网关策略和自动化测试，属于长期有效的兼容性决策。

## 决策驱动因素

- 满足前端到后端链路只放行 GET 和 POST 的明确接口约束。
- 保持 GET 的安全只读语义，避免查询产生业务状态变更。
- 让每项业务操作具有全局唯一、稳定且可审计的路径，避免依赖 HTTP 方法或请求体猜测动作。
- 在后续开发中自动阻止 PUT、PATCH、DELETE 或未限定请求方法的映射重新进入业务接口。

## 备选方案

### 方案 A：保留资源路径并继续使用标准 REST 方法

- 收益：沿用既有调用方，HTTP 语义更接近通用资源建模惯例。
- 成本/风险：不满足已确认的 GET/POST 方法白名单，受限网关或调用链无法统一放行。

### 方案 B：所有写操作改为相同资源路径上的 POST

- 收益：路径变化较少。
- 成本/风险：会话重命名和删除等不同命令会共享同一方法和路径，只能依赖请求体或参数分派，容易产生歧义并降低审计可读性。

### 方案 C：POST 配合显式动作资源

- 收益：满足方法白名单，并用稳定路径清晰区分重命名、删除、停止和重新生成等命令。
- 成本/风险：属于破坏性接口契约变更，旧前端必须与后端协调升级。

## 决策

选择方案 C。面向前端的业务接口只注册 GET 或 POST：

- GET 仅用于查询和 SSE 订阅，不产生业务状态变更。
- 所有创建或状态变更使用 POST。
- 首次提问通过 `POST /api/v1/questions/submission` 原子创建会话、问题和回答，会话列表使用 `GET /api/v1/chats`。
- 会话重命名使用 `POST /api/v1/chats/{chatId}/rename`。
- 会话删除使用 `POST /api/v1/chats/{chatId}/deletion`。
- 回答反馈使用 `POST /api/v1/answers/{answerId}/feedback`。
- 原 PATCH、PUT、DELETE 映射直接移除，不提供并存别名，避免方法白名单出现例外。

每项业务操作的 URL 模板必须全局唯一，禁止创建和列表、上传和列表等操作共享路径后再依靠 HTTP 方法区分。动作路径只改变传输契约，不改变既有 Owner 校验、状态机、幂等、逻辑删除、错误码或响应体语义。删除命令仍按当前领域规则收敛到可重复执行的逻辑删除结果。

一期不注册文件上传、列表或删除接口。后续阶段如重新启用文件能力，其写操作仍使用 POST 和全局唯一动作路径，并需新增契约测试后方可发布。

## 后果

- 正面影响：网关方法白名单可简化为 GET/POST；业务写操作路径可直接识别和审计；前后端契约一致。
- 负面影响：旧版前端调用会收到 `405 Method Not Allowed` 或路径不存在响应，不能与新版后端长期混用。
- 后续工作：前后端必须在同一发布窗口升级；生产网关确认只放行所需 GET/POST 路径；外部调用方如存在，必须在切换前完成盘点和迁移。

## 验证

- Spring MVC 上下文测试扫描实际业务控制器映射，断言每个映射显式且仅使用 GET 或 POST、所有 URL 模板全局唯一，并校验关键动作路径。
- 前端 `HttpQaGateway` 契约测试调用全部普通接口，断言 URL 和方法矩阵只包含 GET 与 POST。
- 仓库文本检查不得在生产控制器、前端 HTTP 网关和生效契约文档中发现 PUT、PATCH 或 DELETE 接口。
- 后端执行 `mvn -B -ntp clean verify`，前端执行 `npm run verify`。

## 回滚或取代

若公司 API 网关标准后续要求恢复资源化 HTTP 方法，需要新的 ADR 取代本决策，并协调前后端、网关和调用方重新发布。回滚代码时必须成对恢复后端映射与前端网关，不能只回滚单侧；数据库和领域状态不需要回滚。
