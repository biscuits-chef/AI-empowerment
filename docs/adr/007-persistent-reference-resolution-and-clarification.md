# ADR-007：持久化指代消解与追问状态

## 状态

已接受。

## 背景

用户会连续提问“它的费率呢”“第二个”等不完整语句。仅把最近消息交给大模型会产生三类风险：历史窗口裁剪后对象丢失、多个候选时静默猜测、进程重启后无法继续追问。追问又不能伪装成失败，否则前端无法把它作为可继续的正常对话轮次。

## 决策

1. GoldenDB 表 `qa_conversation_context` 按 `owner_id + conversation_id` 保存上一意图、已验证实体、来源问题 ID、待追问原因与候选，并使用乐观版本更新。
2. 只允许使用已验证结构化实体完成指代消解；无来源的助手文本和越权候选不能成为指代依据。
3. 低置信度、缺少必需实体或多个候选时，本轮回答进入终态 `NEEDS_CLARIFICATION`，持久化确定性追问文本。
4. 追问分支不调用知识库、业务数据库、证据对账或大模型。SSE 顺序固定为 `metadata → workflow_plan_selected → intent_recognition_started → clarification_required → delta → completed`。
5. 用户下一条消息可用候选序号、完整名称或唯一标识补充；应用层合并原意图并消费待追问状态。仍无法唯一确认时继续追问，不猜测。
6. 两个查询通道接收解析后问题与结构化实体；大模型仍可看到原问题，但事实查询不得只使用裸指代词。

## 后果

- 收益：刷新、历史裁剪和进程重启后仍可继续追问；歧义不会进入事实查询；追问回答具有可审计状态。
- 代价：需要结构化状态迁移、并发版本处理、候选权限过滤和额外测试。
- 限制：当前演示识别器只提供保守规则。生产发布前必须接入受权实体目录、业务别名词典和经标注数据验证的识别器。

## 验证

- 服务测试覆盖可信上下文指代、无来源追问、多候选、序号补充、低置信度和下游零调用。
- SQL 集成测试覆盖上下文持久化、Owner 隔离、候选恢复和乐观版本冲突。
- 前端测试覆盖追问事件、追问终态、下一条补充问题以及刷新后状态恢复。
